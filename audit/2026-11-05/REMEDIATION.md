## Ограничения объёма

- Заказ: до 100000 кодов и 1000 товарных позиций. Импортируемый файл — до 10 МБ; макет — до 100 КБ.
- Полный/асинхронный/альтернативный PDF — до 2000 этикеток. Для больших заказов нужны рулоны до 2000 каждый; запрос не возвращает усечённый успешный PDF.
- Одновременно обрабатываются до двух тяжёлых HTTP-запросов на процесс, до одного на пользователя; время ограничено пятью минутами. Очередь PDF удерживает до восьми ожидающих заданий.
- Списки возвращают страницы до 200 записей и `X-Next-Page`. Текущие интерфейсы объединяют страницы до 10000 записей; превышение даёт явную ошибку. API поддерживает отдельную навигацию по страницам. Аналитика использует SQL, для длинных периодов график агрегируется по месяцам.
- Калибровочный образец первой этикетки активного заказа остаётся доступен до оплаты, в том числе с первым настоящим кодом. Это согласованное существующее исключение.

2. На явно выбранной базе выполнить read-only `node scripts/security-preflight.cjs`. Скрипт печатает только количества проблем, не коды и не секреты. Устранить дубли кодов, несколько активных счетов, неверные индексы и расхождения обязательств после сверки первоисточников. Миграция не удаляет и не выбирает «правильные» финансовые записи автоматически.
3. Выполнить `prisma migrate deploy` штатным способом. Новые миграции: `20261105120000_support_attachment_ownership`, `20261105130000_order_integrity`, `20261105140000_sscc_sequence`. При условии, требующем сверки, миграция откатывает DDL; после устранения причины разобраться со статусом failed migration через штатную процедуру Prisma, не помечать незавершённые шаги применёнными.
4. Для старых неоплаченных заказов подтвердить неизвестные параметры цены. ## A01: секреты и очищенная история

`scripts/prepare-clean-history.py --output <новый-путь-вне-репозитория>.bundle` создаёт отдельный репозиторий: очищает найденные значения и bot-token patterns во всей доступной истории, удаляет исторические пути дампов и приватных env, накладывает текущие исправления и проверяет доступные Git-объекты перед выпуском bundle. Исходные refs, index и remote не меняются; push не выполняется. Замена истории потребует согласования с владельцами копий и повторного клонирования. Проверенная подготовленная копия указана в `evidence/history-preparation.json` после выполнения.

Для ротации нужны новые значения из менеджера секретов и отзыв старых Telegram/SMTP/интеграционных доступов у соответствующих провайдеров. Пароль PostgreSQL меняется согласованно с конфигурацией сервиса; один новый env не меняет пароль роли в существующем volume.

`scripts/rotate-encryption-key.cjs` использует явно заданные `DATABASE_URL`, `OLD_ENCRYPTION_SECRET`, `NEW_ENCRYPTION_SECRET`. По умолчанию проверяет расшифровку без записей. Только `--apply` перешифровывает пароли аккаунтов в транзакции, сбрасывает сохранённые интеграционные сессии, отзывает JWT-сессии через tokenVersion и погашает OTP. Значения/открытые пароли не печатаются. Скрипт не выполнялся на рабочей БД. При переключении ключа старый процесс должен быть остановлен; затем применяются новый ключ и новый JWT_SECRET и проверяется вход/расшифровка на стенде.

Само переписывание Git не отзывает раскрытые секреты. Пока реальные ключи не отозваны, опубликованная история не заменена и копии не обработаны, **A01 не считается полностью устранённой**.
