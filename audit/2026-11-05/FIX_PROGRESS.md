## Шаг 1 — A02: чужой аккаунт интеграции и утечка секретов

**Статус: исправлено локально, проверено; не развёрнуто.**

Изменены `backend/src/services/markirovkaCards.service.ts` и `backend/src/controllers/markirovkaCards.controller.ts`. Добавлены регрессионные тесты `backend/tests/markirovka-cards-security.test.cjs`.

- При смене `accountId` проверяется владелец аккаунта относительно владельца карточки. Правило действует и при редактировании администратором карточки клиента. Чужой или отсутствующий аккаунт возвращает 403 до записи.
- Проверка статуса, отправка, публикация и удаление отвергают уже существующие чужие/нарушенные связи до использования credentials и внешнего вызова.
- Ответы с данными аккаунта допускают только `id`, `name`, `login`, `categories`. Токены, API-ключи, зашифрованный пароль и будущие дополнительные поля аккаунта не сериализуются.
- Список карточек скрывает метаданные аккаунта из старой межклиентской связи. Обычное редактирование, очистка привязки и чтение карточки без аккаунта сохраняются.

Проверено: `npm run build` в backend; `node --test tests/*.test.cjs` — **36/36**, включая 8 новых тестов; `git diff --check` без ошибок пробелов. Новые тесты используют mock БД/интеграций, исходящие запросы блокируются либо заменяются фикстурой. Боевые данные не читались и не исправлялись.

Перед развёртыванием нужна отдельная сверка уже существующих связей карточка–аккаунт в разрешённой среде. Такие карточки теперь безопасно блокируются; их исправление не выполнено массовым обновлением. Возможная прежняя утечка ключей требует действий по A01 — изменение кода не отзывает раскрытые секреты.

**Остальные 23 находки в этом шаге не исправлялись.** Старые F-пробы предназначены для исходного коммита; после исправления A02 их прежний общий успешный результат не ожидается. Для текущей реализации использовать штатные регрессионные тесты.

Следующий отдельный шаг: A03 — единая проверка права на получение неоплаченных кодов через реестр, детали, файлы и печать.

## Шаг 2 — A03: обход оплаты при получении кодов

**Статус: исправлено локально, проверено; не развёрнуто.**

Добавлена общая политика `backend/src/utils/orderCodeAccess.ts`; применена в контроллерах заказов, генерации этикеток и операций маркировки. Добавлены `backend/tests/order-code-access.test.cjs`.

- Клиент получает коды собственного активного заказа после оплаты **либо** явного `printAllowed` администратора. Для CANCELLED/REFUNDED доступ закрыт даже при оставшемся разрешении печати. Административный доступ сохранён.
- Реестр фильтрует по этому правилу строки, поиск, статистику, список заказов и предварительное заполнение кодов.
- Детали заказа и ответы создания/изменения/синхронизации сохраняют метаданные, но скрывают коды эмиссии, содержимое отчётов и потенциально содержащие коды ошибки до разрешения доступа. Ссылки на файлы заменяются защищёнными API-маршрутами: интерфейс видит наличие файла, а скачивание повторно проверяет права.
- Скачивание файла, чтение содержимого, список отдельных кодов и все способы печати используют общую проверку. Индивидуальный макет должен иметь актуальный APPROVED; старое время согласования не отменяет последующий CHANGES_REQUESTED.
- Альтернативная печать требует разрешённый заказ для клиента, включая обращение по ID эмиссии. Переданные клиентом произвольные `codes` не обходят проверку: печатаются данные разрешённого заказа из БД. Администратор по-прежнему может печатать явно переданный набор кодов.
- История эмиссии и квитанции также учитывают оплату. Payload ранее сохранённых операций с недоступным заказом скрывается; получение квитанции блокируется до внешнего запроса.
- Сохранено прежнее исключение для калибровки: один образец первой этикетки активного заказа, в том числе с первым настоящим кодом. `sample` не разрешает произвольный индекс или партию. Это не обещание полного отсутствия любого отдельного кода до оплаты.

В этой цепочке оказалось необходимо проверять доступ до восстановления кодов в отчёте о нанесении. Это **частично закрывает A04**: чужой/неоплаченный `orderId` теперь отвергается до чтения кодов и отправки. A04 пока не считается полностью закрытой: остаются точное сопоставление укороченных кодов вместо первых N строк и согласованность аккаунта/заказа.

Проверено: сборка backend успешна; весь набор **49/49** тестов, включая 13 новых; `git diff --check` без ошибок пробелов. Лог: `evidence/fix-a03-tests.log`. Отрицательные сценарии не допускают немокированные обращения к БД/сети; положительные PDF-сценарии используют фиктивный HTTP-генератор. Проверена совместимость использования полей URL в коде личного кабинета; полный браузерный сценарий и production не запускались.

Исходный отчёт не переписан: он описывает состояние проверенного коммита. Локально закрыты A02 и A03; A04 — частично. Остальные находки сохраняют свой статус. Следующий отдельный шаг — оставшаяся часть A04.

## Шаг 3 — A04: точное восстановление кодов и аккаунт отчёта о нанесении

**Статус: исправлено локально, проверено; не развёрнуто.**

Добавлен `backend/src/services/utilisationCodes.service.ts`, обновлён обработчик `createUtilisation`, добавлены `backend/tests/utilisation-codes.test.cjs`.

- Вместо первых N строк выбираются кандидаты по полному GTIN и серийному номеру с границей GS. Результат сохраняет исходный порядок и состав запроса. Цифры `91`/`92` внутри серийного номера не определяют границу.
- Полный код должен точно совпадать с кодом заказа; изменённый криптохвост не подменяется сохранённым. Сокращённый код восстанавливается только при одном однозначном соответствии. Нормализуются транспортные CR/LF и текстовые обозначения `<GS>`.
- Неизвестные, неоднозначные, пустые, нестроковые и повторяющиеся значения останавливают весь отчёт до отправки. Это включает повтор одного кода в полном и сокращённом виде. Ошибка БД больше не игнорируется с последующей отправкой сокращённых значений.
- Выборка разбита на группы до 100 идентификаторов. `%`, `_` и обратная косая черта экранируются для буквального сопоставления в SQL; это проверено реальным LIKE/ILIKE в PGlite. Основание: [Prisma о фильтрации](https://docs.prisma.io/docs/orm/v6/prisma-client/queries/filtering-and-sorting), [PostgreSQL 15 о шаблонах LIKE](https://www.postgresql.org/docs/15/functions-matching.html).
- Для заказа с эмиссией требуется её сохранённый аккаунт. Другой явно выбранный аккаунт, несколько аккаунтов эмиссии, отсутствующая или неактивная привязка приводят к ошибке. Автоматического переключения на произвольный активный аккаунт нет.
- Для загруженных кодов без эмиссии требуется аккаунт владельца заказа, в том числе при действии администратора. Для сохранённой привязки эмиссии администратор может использовать привязанный клиентский/служебный аккаунт; клиент — только свой. Если ID не задан, выбор допустим лишь при одном подходящем активном аккаунте.
- Товарная группа должна совпадать с заказом; при отсутствии параметра используется группа заказа. Без `orderId` разрешены только полные переданные коды, без восстановления из чужих данных.

Проверено: сборка backend успешна, весь набор **67/67** тестов, включая 18 новых; `git diff --check` без ошибок пробелов. Лог: `evidence/fix-a04-tests.log`. Внешний клиент заменён фикстурой, реальные HTTP-вызовы запрещены, SQL-тест использует БД в памяти.

Старые коды с уже утраченными GS не восстанавливаются предположениями: требуется достоверный исходник и отдельное исправление A07. Заказы с несколькими аккаунтами эмиссии требуют сверки привязок перед отправкой; автоматическое разбиение по аккаунтам не добавлялось. Production-данные и ранее ошибочные отчёты не изменялись. Частичные сбои после принятия отчёта внешней системой и идемпотентность остаются отдельной работой по согласованности интеграций.

Локально закрыты **A02, A03 и A04**. Следующий отдельный шаг — **A05: подделка права на вложение через публичную заявку**.

## Шаг 4 — A05: владелец вложения обращения

**Статус: исправлено локально, проверено; не развёрнуто. Требуется новая миграция БД.**

В схему Prisma добавлена `SupportAttachment`: уникальное имя файла, оригинальное имя, владелец по `User.id` и связь с `ServiceLead`. Миграция — `20261105120000_support_attachment_ownership`.

- Авторизованный обработчик обращения создаёт заявку и запись вложения одним вложенным Prisma write. Владелец берётся из найденного авторизованного пользователя; поля владельца/вложений из тела запроса не используются.
- Скачивание клиентом проверяет точный `filename` и `ownerId`. Email и подстроки в notes больше не участвуют в авторизации. Публичная заявка не может назначить владельца вложения.
- Проверка доступа выполняется до проверки наличия файла. Смена email не лишает владельца доступа, совпадающие email не дают его другому пользователю.
- Имена новых файлов содержат случайный UUID; параллельные загрузки одинакового оригинального имени не перезаписывают друг друга. При отказе валидации/сохранения загруженный файл удаляется только из проверенного каталога bug-reports.
- Формат notes и URL вложения сохранён для административного интерфейса. Старые файлы без доверенной записи доступны только администратору. Миграция намеренно не выводит владельца из старых email/notes; восстановление клиентского доступа возможно только после отдельной сверки доверенных данных.

Проверено: сборка backend успешна; весь набор **76/76** тестов, включая 9 новых. Есть локальная HTTP-проверка настоящей multipart-загрузки и скачивания владельцем/чужим клиентом, проверка поддельной публичной заявки, отказа БД и очистки файла. Миграция проверена в PGlite на свежей схеме и при обновлении со старыми заявками: данные сохранены, ложные права не создаются, уникальность имени и внешние ключи работают. Лог: `evidence/fix-a05-tests.log`; `git diff --check` без ошибок пробелов.

Письма и Telegram заменены заглушками, реальные уведомления не отправлялись. Миграция не применялась к рабочей или production-БД: при развёртывании её необходимо выполнить штатным `prisma migrate deploy` до запуска новой версии backend. При остановке процесса между записью файла Multer и записью в БД может остаться файл без владельца; клиентам такой файл недоступен.

Локально закрыты **A02–A05: 4 из 24**, осталось **20**. Следующий отдельный шаг — **A06: доверенные адреса интеграций, SSRF и отправка общего ключа**.
