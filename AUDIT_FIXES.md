# Исправления по техническому аудиту

Изменения подготовлены локально 3 ноября 2026 года. Production-сервисы и настройки зоны Cloudflare не изменялись.

## Безопасность и корректность

- При смене роли или пароля администратором увеличивается версия сессий и очищается кеш. Проверка прав использует актуальную роль из БД. Обход maintenance также проверяет действующую роль и версию токена.
- Просроченные и отозванные JWT возвращают 401. Ошибка БД возвращает 503. Кабинеты сохраняют токен при временном сбое и показывают кнопку повторного подключения.
- JWT больше не принимается из URL. Вложения баг-репортов загружаются с Authorization в Blob URL с освобождением ресурса при закрытии. Логи приложения и Caddy маскируют чувствительные параметры.
- Оба этапа регистрации проверяют типы, пароль, email, БИН и телефон; на финальном этапе повторяется проверка телефона.
- Оплата заказа и связанного счета использует общий сервис с одинаковым порядком блокировок строк. Списание, статусы и история платежа фиксируются одной транзакцией. Неуспешный callback не перезаписывает успешный платеж.
- TLS SMTP проверяется по умолчанию. Добавлен `SMTP_TLS_SERVERNAME` для подключения по IP с проверкой DNS-имени провайдера.

## Доступность и эксплуатация

- Caddy доверяет клиентскому IP только от опубликованных диапазонов Cloudflare и передает backend нормализованный X-Forwarded-For. Ограничитель запросов корректно группирует IPv6-подсети.
- Переиспользование backend-соединений Caddy ограничено 30 секундами, ниже 65 секунд Node.js. Опубликован UDP/443 для HTTP/3. Добавлены канонический www-редирект и корректные переходы со старых /lk и /admin.
- `/api/ready` проверяет доступность БД с ограничением времени. Docker healthcheck использует readiness; пользовательский `/api/health` сохраняет прежний контракт. Введены ограничения пула БД и ресурсов контейнеров, доступные через переменные окружения.
- Бэкап останавливается при ошибке pg_dump, проверяет gzip и заголовок дампа, затем публикует файл атомарно. Секреты больше не выводятся скриптом деплоя, dotenv не выполняется через eval.
- Удален автоматический fallback на db push. Добавлена полная baseline-миграция. Перед принятием baseline для существующей БД проверяется отсутствие расхождения схемы. Ошибка миграций останавливает запуск.
- Очередь PDF освобождает слот после фактической остановки задания, включая отмену и таймаут; завершение учитывается один раз. Запуск Chromium объединен для одновременных запросов, переразвертывание браузера ждет завершения активных документов.

## Frontend и зависимости

- Общий список React/SSG-маршрутов обеспечивает прямые переходы на все статические языковые варианты.
- Страницы кабинетов и PDF-экспорт загружаются по требованию. Добавлены экраны восстановления при ошибках загрузки. Исправлено перекрытие cookie-баннера кнопкой WhatsApp.
- HTML перепроверяется при загрузке. Для landing заранее создаются gzip-версии ресурсов. Добавлена CSP, совместимая с используемыми аналитикой, NCALayer и Cloudflare Challenge.
- Docker использует Node.js 22 и npm ci. Обновлены зависимости, React Router и Vite. Добавлены автоматические проверки CI.

## Проверки

```sh
npm ci --prefix backend
npm test --prefix backend
python -m unittest discover -s scripts/tests -v
# Выполнить npm ci и npm run build в остальных четырех приложениях.
node scripts/browser-smoke.cjs
python scripts/check-availability.py --origin 185.200.86.23 --samples 5
```

Backend-тесты проверяют отзыв прав и сессий, сохранение сессии при недоступной БД, атомарность платежей на транзакционном тестовом двойнике, очередь PDF и маскирование логов. Baseline и все исторические миграции проверяются на пустой PostgreSQL-совместимой БД PGlite. Тесты бэкапа используют подставной Docker и не обращаются к реальной БД. Browser smoke использует отдельный профиль Chromium, локальные сборки и API fixtures. Секреты и реальная авторизация для этих тестов не нужны.

Парсинг нового Caddyfile и тест конфигураций Nginx выполнены существующими production-бинарниками без применения конфигурации. Docker Compose проходит проверку. Проверка схемы рабочей БД 3 ноября дала `No difference detected`.

## Перед production-деплоем

1. Заменить опубликованные в чате ключи Cloudflare/R2; не добавлять их в репозиторий.
2. Проверить настройки SMTP. На момент проверки соединение идет на IP, сертификат имеет имя `mail.tormag.kz`; цепочка и проверка этого имени проходят. Если это подтвержденное имя вашего почтового провайдера, установить на сервере `SMTP_TLS_SERVERNAME=mail.tormag.kz` и `ALLOW_SELF_SIGNED_SMTP=false`. Альтернатива — корректный сертификат для собственного почтового имени. Одно изменение значения по умолчанию не переопределяет существующую явную переменную `.env`.
3. Согласовать ресурсные лимиты с максимальным объемом PDF. Сервер имеет около 1,6 GiB RAM; крупные партии требуют отдельной нагрузочной проверки, при необходимости увеличения RAM и лимитов.
4. Выполнить резервное копирование и `bash scripts/deploy.sh` после разрешения владельца на production-развертывание. При обнаружении drift скрипт остановится; ручное db push не использовать.
5. Повторить проверку IPv4/IPv6 после выкладки. Исправления проекта не доказывают устранение зависания на пути клиент → Cloudflare.

## Что известно о Cloudflare

Через предоставленный токен проверены правильные A-записи origin и Full (strict). Пользовательских origin AAAA нет. Правило Managed Challenge ограничено страницей входа admin.tanbox.kz. IPv6, HTTP/3 и 0-RTT включены; Rocket Loader выключен. Изменения этих настроек не применялись.

В исходной диагностике 4 из 12 запросов через IPv6 зависли после успешного TLS без HTTP-ответа; 9 из 9 IPv4 и 6 из 6 прямых origin-запросов прошли. Один помеченный зависший запрос отсутствует в origin access.log. Постоянное отключение IPv6, HTTP/3 или защиты без отдельного контрольного теста не является доказанным исправлением. `check-availability.py` сохраняет временные метки и уникальные идентификаторы для сопоставления с журналами и обращением в поддержку.

Полные Docker-образы локально не собирались: Docker Desktop engine недоступен. Сборки исходников и проверки конфигураций выполнялись отдельно. Конкурентные платежи на реальном PostgreSQL, реальные платежные callbacks, отправка почты и максимальные PDF-партии требуют проверки в staging.
